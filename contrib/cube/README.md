# cube, in Go

A port of PostgreSQL's [`contrib/cube`](https://www.postgresql.org/docs/current/cube.html)
(version 1.5) to Go: the `cube` data type for multi-dimensional boxes and
points, with its functions, operators, and btree and GiST operator classes
(including k-NN ordering by `<->`, `<#>`, `<=>` and `~>`), as a drop-in
replacement.

Values have upstream's binary layout (the varlena of `NDBOX`: a header
with the number of dimensions and the point flag, then `float8`
coordinates), so tables, indexes and binary `COPY` data written with the
C module work unchanged, and every function is exported under upstream's C
symbol: databases created with any upstream version (1.2's install script
and its update scripts included) work with this library.

| Go source  | Ported from (PostgreSQL 18)                                     |
|------------|-----------------------------------------------------------------|
| `main.go`  | `cube.c`: the type (`//gopgext:type` over `pg.Varlena`), input/output, send/receive, constructors, accessors, `cube_enlarge` |
| `parse.go` | `cubescan.l` and `cubeparse.y`: a hand-written scanner and parser that reproduce flex's longest match and Bison's error detection (see below) |
| `ops.go`   | `cube.c`: comparison, containment, overlap, union, intersection, size, the three distances |
| `gist.go`  | `cube.c`: `gist_cube_ops` with gopgext/gist (Guttman's quadratic split, k-NN distances), exported as `g_cube_*` with `//gopgext:alias` |
| `sql/cube.sql` | `cube--1.2.sql` with the 1.3, 1.4 and 1.5 update scripts applied, less the type and its I/O functions (generated by gopgext) |

```sh
gopgext install -version 1.5 -trusted -comment 'data type for multidimensional cubes' contrib/cube
```

## gopgext features it brought

- `pg.FormatFloat8`: `float8`'s output (shortest exact text, or per
  `extra_float_digits`), which `cube_out` uses for coordinates.
- gopgext/gist: queries of fixed-size types (the `int4` coordinate of
  `ORDER BY c ~> 3`), keys of the indexed type itself (no `STORAGE`), and a
  no-op `gopgext_gist_decompress` for old install scripts.
- `//gopgext:alias`: framework support functions under upstream's symbols
  (`g_cube_consistent` ...), so upstream's scripts and existing databases
  find them; libraries now link with `-Bsymbolic` so that an alias calls
  its own library's function when several gopgext libraries are loaded.

## Differences from upstream

- `cube_union(c, c)` with the very same in-memory value as both arguments
  returns it unchanged in C (a pointer comparison) and normalized here; the
  results differ only for values stored with swapped corners, like
  `'(2),(1)'` (the port returns `(1),(2)`).
- `cube_in`, `cube_out`, `cube_recv` and `cube_send` are created by
  gopgext with parameter names and comments (upstream's have neither).
- GiST penalties and page splits are upstream's algorithms, except that
  gopgext/gist turns negative or NaN penalties into 0, so trees can differ
  slightly for such keys (searches find the same rows).

## Parser

The parser reports what upstream's Bison parser reports, error for error:
`syntax error at or near "x"`, `at end of input`, different dimensions,
more than 100 dimensions, out-of-range numbers (overflow, or underflow to
zero; subnormal numbers are accepted, like `float8in`). Two Bison details
matter: a form is reduced (and its numbers checked) as soon as the parser
has seen the token after it, so `'1e400 x'` is an out-of-range error, not a
syntax error; and bytes from 0x80 come out of the scanner as negative
`char`s, which Bison takes for the end of the input, so `'(1)é'` is the
point `(1)` (and `'(1é'` a syntax error at the byte `\xC3`).

## Verification

**Upstream regression tests**: `pg_regress` with `contrib/cube`'s `sql/`,
`expected/` and `data/` unmodified passes against this port: `cube` and
`cube_sci` on PostgreSQL 18 (REL_18_STABLE) and on PostgreSQL 14
(REL_14_STABLE's files).

**Tests**: `test.sql` checks output, points, binary `COPY` round trips, the
GiST index (`&&`, `<@`, k-NN by `<->` and `~>`, index-only scans) against
sequential scans.

**Differential test**: `differential.sql` declares the original C
library's functions (installed as `cube_c.so`) on the port's type and
compares both on generated input: cubes by their `send()` bytes (point
flags and NaN bits included), errors by SQLSTATE, message and detail. With
`n=20000`, 0 mismatches on PostgreSQL 18 and 14:

| Function(s) | Compared (PostgreSQL 18) |
|-------------|-------------------------:|
| `cube_in`: numbers in every scanner form, inf/NaN spellings, huge/tiny exponents, all four forms, 99-101 dimensions, token soup, trailing garbage and non-ASCII bytes (332 distinct errors) | 20,000 |
| `cube_out` with `extra_float_digits` 1, 0, 3, -5, -15 | 2,984 × 5 |
| `cube_send`, `cube_size`, `cube_dim`, `cube_is_point` | 2,984 each |
| `cube_ll_coord`, `cube_ur_coord`, `cube_coord`, `cube_coord_llur`, `cube_subset`, `cube_enlarge`, `cube(cube, float8[, float8])` with indexes -3..201 | 29,840 each |
| `cube_cmp`, `cube_contains`, `cube_overlap`, `cube_union`, `cube_inter`, three distances | 5,968 each |
| `cube(float8[], float8[])`, `cube(float8[])`, `cube(float8[, float8])` with NULLs and length mismatches | 4,000 each |

**Upgrades**: with upstream's older scripts installed, `CREATE EXTENSION
cube VERSION '1.2'` (with its compress/decompress support functions and
`@`/`~` operators), a GiST index on it, and `ALTER EXTENSION cube UPDATE`
work on this library.
