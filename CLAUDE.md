# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

gopgext is a CLI that builds PostgreSQL extensions from plain Go code using TinyGo. Functions in package `main` marked with `//gopgext:function` become SQL functions; gopgext generates the C glue, Go wrappers, `CREATE FUNCTION` script and control file. The user-facing reference is the website in `site/` (Hugo, published to GitHub Pages by `.github/workflows/pages.yml`): guides in `site/content/docs/` (type mapping, function options, `gopgext/pg`, frameworks, limitations) and an API reference generated from the `_files/lib` packages' doc comments by `site/apidoc` (into the gitignored `site/content/api/`). README.md is a short overview that links to it. Keep the docs in sync when changing behavior. The theme in `site/themes/gopherdocs/` is shared with gokm's site: keep the two copies identical.

## Commands

```sh
make                      # build ./gopgext (go build -o gopgext .)
make test                 # go vet ./... && go test ./...
go test ./internal/build -run TestScanSignatures      # single unit test
go test ./internal/build -run TestGenGolden -update   # rewrite testdata/*.golden after changing codegen
make pgtest PG_CONFIG=/path/to/pg_config              # integration tests against a real PostgreSQL
sh test/run.sh [pg_config] examples/hello             # integration test for selected projects only
make site                 # build the website into site/public (make site-serve: preview it)
make clean
```

Integration tests need TinyGo (tested 0.43.0), PostgreSQL 14+ server dev files (`pg_config`, PGXS), `make`, a C compiler and `objcopy`; Linux x86-64 only. `test/run.sh` installs each project into the given PostgreSQL (may need write access to its pkglibdir/sharedir), starts a throwaway cluster in `_pgtest/<version>/`, and runs every `test*.sql` in its own psql session with `ON_ERROR_STOP` — tests assert by raising errors. Conventions per project dir: `build-flags` (extra gopgext flags), `expect-log` (lines required in the server log), `*.fatal.sql` (must kill the session, psql exit code 2). Any `TRAP:`/`PANIC:`/signal termination in the server log fails the run. `make pgtest` runs everything twice: normally and with the examples in `shared_preload_libraries` (port 5498). A new example or contrib port must also be added to `PRELOADED` in the Makefile (the second run, with `shared_preload_libraries`); a project with a `preload` file is always preloaded. The patched-out TinyGo files are `excludedFiles` in `internal/assets`; a TinyGo release that renames them fails early.

## Architecture

Two Go packages do the work on the host side:

- `internal/build` — the pipeline (`build.go`), scanning of the main package via go/ast (`source.go`: `//gopgext:function`, `//gopgext:type`, `//gopgext:ldflags`, and structs used as row results; types are collected across all files first, then functions), and code generation with `text/template` (`gen.go`: Go wrappers, per-struct row fillers, C V1 functions, SQL install script, control file, linker `exports.map`). Generated output is pinned by golden files in `internal/build/testdata/` (`gen.*` and `types.*`).
- Type mapping lives in `scalars` (source.go): `pg.X` types are rewritten to `_gopgext_fmgr.X` in generated code (aliases of `lib/internal/core` types), `*agg.State` to `_gopgext_agg.State`, and `*trigger.Data`/`*trigger.Event`/`*trigger.Row` to `_gopgext_trigger.*` (a function whose only parameter is a `*trigger.Data`/`*trigger.Event` is a trigger/event trigger function: `checkTrigger` in source.go, `triggerCall` in gen.go; these are the only framework types the generator knows). A `//gopgext:type` is passed as its representation scalar and converted to the named Go type in the wrapper (`conv` in gen.go; arrays of it use the fmgr `...Of` functions, which take the element type from the function's signature at run time). A `//gopgext:type` on a struct is a composite type: generated `_gopgext_read_S`/`_gopgext_row_S` functions read and build its rows. `pg.AnyElement`/`pg.AnyArray` (polymorphic) get their actual type from `get_fn_expr_argtype`. The SQL script creates shell types, their I/O functions, `CREATE TYPE`s, composite types, then all other functions, then `sql/*.sql`.
- `internal/assets` — everything under `_files/` is `go:embed`ded and materialized into `~/.cache/gopgext/root-<hash>` (or `$GOPGEXTCACHE`). The hash covers the embedded files and the system TinyGo root/version, so editing assets invalidates the cache automatically. `_files/` starts with `_` so the host `go` tool ignores the Go files in it — **they only compile under TinyGo with the custom target**, so `go vet ./...`/`go test ./...` do not check them; only `make pgtest` exercises them.

Build pipeline (`build.Build`):
1. Scan project signatures, write generated wrappers into a work dir alongside a `go.work` that maps module `gopgext` to the materialized `lib/`.
2. `tinygo build -target=<_files/target.json>` with `TINYGOROOT` pointed at a mirror of the system TinyGo root plus `_files/overlay/` (adds the `pgext` runtime platform: `runtime_pgext.go`, `rand_pgext.go`). The target is hosted Linux (no `baremetal` tag), so `syscall`/`os` are TinyGo's libc-based Linux ones; `runtime_unix.go` (which owns `main`, signals and its own heap) is patched out in favour of `runtime_pgext.go`.
3. `objcopy` strips debug info and localizes every symbol except `keptSymbols` (`gopgext_go_*`, `tinygo_pgext_*`, `tinygo_scanstack`), so multiple Go extensions can coexist in one backend.
4. PGXS compiles `csrc/runtime.c`, `csrc/spi.c`, generated `functions.c`, project `csrc/*.c`, framework C glue, and `go.o` into `<name>.so`, with a version script exporting only `Pg_magic_func`, `_PG_init` and the SQL-visible symbols (including `//gopgext:alias` wrappers, generated into `functions.c`), linked `-Bsymbolic` so calls between exported functions stay inside the library.
5. Emit `<name>.control` and `<name>--<version>.sql` (generated `CREATE FUNCTION`s + framework `install.sql` + project `sql/*.sql` in name order).

Embedded Go library (`_files/lib/`, module `gopgext`, imported by user code):
- `pg` — public API (SPI queries, errors with SQLSTATE, logging, GUC settings, interrupts).
- `fmgr` — argument/result marshalling used by generated wrappers (`Arg`, `ArgPtr`, `ArgArray`, ... / `Return*`; the suffix per `TypeKind` is in `gen.go`'s `kindSuffix`).
- `internal/core` — shared state (call sequence, read-only flag) and C bindings.
- `fdw`, `http`, `gist`, `gin`, `spgist`, `brin`, `am`, `agg`, `selectivity`, `trigger`, `hooks`, `auth`, `shmem`, `bgworker`, `xact`, `intercept`, `tsearch`, `subscript`, `tablesample` — "framework" packages: importing one makes the build pull in `_files/frameworks/<pkg>/` (C glue, optional `ldflags` and `install.sql`), detected via `tinygo list -deps`. Framework C code calls Go by building a `LOCAL_FCINFO` with plain Datum arguments and calling `gopgext_invoke` with an exported `gopgext_go_*` Go function, which reads them with `fmgr.Call.Datum` (GiST structures never reach Go). The index operator class packages dispatch each support function to the `OpClass` registered under the name of its operator family (`pg_amproc` lookup cached in `fn_extra`; brin uses the index's `rd_opfamily`); `selectivity` dispatches by SQL function name, `am` by access method (`pg_am.amhandler`). `am` keeps Go away from buffers: Go sees a record store (meta blob + chains of records on index pages, every change one GenericXLog record, writers serialized by a page-0 heavyweight lock). `agg` never runs Go from PostgreSQL callbacks: memory-context reset callbacks only record freed state ids, which Go drains on its next call. `hooks` installs every query-processing hook (keeping pg_stat_statements' nesting level rules) and calls Go only before/after the C planner/executor with a plain event struct. Its execute decision runs before `ExecutorStart` (so Go can request per-node instrumentation), and `Statement.Explain` runs EXPLAIN's printing in C during the `Executed` event. `auth` installs `ClientAuthentication_hook`/`check_password_hook`; a Go error is raised after Go returns (FATAL during authentication). `shmem` registers objects during preload (shmem_request_hook on 15+, direct requests on 14) and attaches them in shmem_startup_hook; Go types stored there are checked with reflect to be pointer-free. `bgworker` registers static background workers during preload whose entry point (`gopgext_export_bgworker_main`: `gopgext_export_*` symbols are exported for PostgreSQL to look up by name) runs one long Go call; the worker manages its own transactions (`Context.Transaction`), waits on its latch (`Context.Wait`, woken by `Handle.Wake` through a shared-memory slot holding its PGPROC) and stops on SIGTERM. SPI refuses to run outside a transaction. `xact` registers transaction callbacks on first use: only PRE_COMMIT/PRE_PREPARE call Go (the scheduled `Callback`s, a bitmask in C); commits and aborts just bump `xact.ID`, and subtransaction ends are logged in C once Go called `xact.Current`, for `RolledBack`. `intercept` installs planner and ExecutorRun hooks: per table it asks Go for a policy (cached in a hash invalidated by relcache callbacks; RLS, other UPDATE triggers and inheritance children block interception in C), rewrites a matching UPDATE into a SELECT of tableoid/pk/new values whose target-list column names carry the markers (`ix:<ext>:...`, so cached plans work and several extensions can coexist), runs it itself and passes rows to Go in batches of 1000, setting es_processed; watched columns get a hidden RETURNING (row keys) or a per-table report (MERGE, ON CONFLICT, RETURNING, CTEs). `csrc/relation.c` backs `pg.LookupRelation` (syscache/relcache, no SPI), `pg.InvalidateRelation`, `pg.RunAs` and binary images (`pg.Image`/`FromImage`).
- `pg.Record` results (`record`/`SETOF record`): `csrc/record.c` reads the caller's row type (`get_call_result_type`/`rsinfo->setDesc`); Go converts each value to a Datum or to text for the column's input function. `core.Call` is the running `gopgext_call` (set by `fmgr.Call.Begin`), used by `pg.ResultColumns`.

Runtime model (important when touching C runtime or Go runtime overlay): a backend is single-threaded, so there is no scheduler and no goroutines; Go runs on the backend's own stack only while PostgreSQL calls in. `gopgext_invoke` (runtime.c) enters Go and raises any reported error only after Go returns — a PostgreSQL `ereport`/`longjmp` must never unwind through Go frames. C helpers that may raise catch the error; unrecoverable ones make Go panic-unwind and the original error is re-thrown. The Go heap is a conservative-GC heap `mmap`-reserved at load (`-heap-size`/`-heap-max`); exhausting it exits the backend with `FATAL`. Results are copied into `palloc` memory before returning.

`contrib/` holds ports of PostgreSQL contrib modules that must only use the public gopgext packages (extend the framework rather than adding project C): `isn` and `fuzzystrmatch` (with `differential.sql` comparisons against the C originals), `pg_stat_statements` (needs the `preload` marker; validate with upstream's regression suite via pg_regress). `examples/` are real extensions (`vector` — pgvector's core on `//gopgext:type` — and `geo` — a GiST-indexed PostGIS-like type); `test/fixtures/` cover failure modes (bad init, OOM, multiple extensions in one backend, http). Their `go.mod` files have no `require` for `gopgext`; resolution comes from the generated `go.work`. Never commit `go.work` files (gitignored; `gopgext init` writes machine-specific ones for editor support).
